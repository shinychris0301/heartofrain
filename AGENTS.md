# AGENTS.md — Heart of the Rain (Unity match-3)

Instructions for coding agents (Codex and others) working in this repository.
Read this whole file before touching code. Task prompts live in `docs/codex/prompts/`;
the issue register is `docs/codex/FINDINGS.md`; product decisions are `docs/codex/DECISIONS.md`.

## 1. What this project is

- A portrait mobile match-3 game built with **Unity 2022.3.62f3**, built-in render pipeline, UGUI.
- Canonical project: `Unity/` (`Unity/Assets/HeartOfTheRain/**`). 50 Chapter 1 levels.
- **You cannot run Unity.** Unity compilation, Play Mode and player builds are verified by a human
  after your change. Everything you can verify must be verified with the headless harness (§6).

## 3. Language, API and file-format constraints

- **C# 9 maximum** (Unity 2022.3). Do not use: file-scoped namespaces, global usings, `record`,
  `init` accessors, raw string literals, `required`, list patterns, or any C# 10+ feature.
- **.NET Standard 2.1 API surface only** in `Unity/Assets/**`. Do not use APIs added after it
  (e.g. `Enumerable.Chunk/MaxBy/MinBy/DistinctBy/Order`, `System.Text.Json`, `DateOnly`, `Random.Shared`).
- No new Unity packages and no NuGet packages in `Unity/`. Do not edit `Unity/Packages/manifest.json`.
- `UnityEditor` may only be referenced from files inside a folder named `Editor/`.
- There are **no `.asmdef` files**: everything compiles into `Assembly-CSharp` / `Assembly-CSharp-Editor`.
  Do not add asmdefs (that is a separate, deferred refactor).
- Input uses the **legacy Input Manager** (`UnityEngine.Input`). Existing `#if ENABLE_INPUT_SYSTEM`
  blocks must be preserved as-is.
- Text files are **UTF-8 without BOM, LF line endings**. Preserve both. `LocaleCatalog.cs`,
  `StoryLocaleCatalog.cs` and `JourneyText.cs` contain non-ASCII text — never re-encode them.

## 4. Code style

- Match the surrounding code. Many files use dense, multi-statement lines.
- **Do not reformat code you are not changing.** When you change one statement on a dense line you may
  split *that statement* onto its own line; leave the rest of the line byte-identical. Reviewers must be
  able to read your diff.
- Keep the existing naming (camelCase fields, PascalCase members, string families such as `"gem"`,
  `"power"`, statuses such as `"Playing"`, `"Won"`, `"Out of moves"`).
- Put new rule/state logic in **pure classes** (no `UnityEngine` dependency, or only the types provided
  by the headless shim) so the harness can test them. Keep MonoBehaviour changes to thin wiring.
- New user-visible English strings must be added to
  `Unity/Assets/HeartOfTheRain/App/Localization/Runtime/LocaleCatalog.cs` with all five locales in the
  existing order `en, es, fr, de, ru` (`{"English",new[]{"English","Español","Français","Deutsch","Русский"}}`).
  `GameLocale.T` matches `{0}` placeholders as patterns. List every new string in your final report so a
  native speaker can review the translations.
- Comments: only where the existing code would have one (short, explaining *why*).

## 5. New files in `Unity/Assets`

Every new file **and folder** under `Unity/Assets` needs a `.meta` file with a new random 32-hex-digit
lowercase GUID that does not already exist in the repo (check with a search). Template for a `.cs` file:

```
fileFormatVersion: 2
guid: <32 lowercase hex chars>
MonoImporter:
  externalObjects: {}
  serializedVersion: 2
  defaultReferences: []
  executionOrder: 0
  icon: {instanceID: 0}
  userData:
  assetBundleName:
  assetBundleVariant:
```

For a new folder use:

```
fileFormatVersion: 2
guid: <32 lowercase hex chars>
folderAsset: yes
DefaultImporter:
  externalObjects: {}
  userData:
  assetBundleName:
  assetBundleVariant:
```

## 6. Verification (mandatory)

After task 01 is merged, a headless harness exists at `Tools/HeadlessTests/`. It compiles the pure
gameplay/app sources from `Unity/Assets` against a small `UnityEngine` math shim and runs tests,
including full campaign validation (all 50 levels + the 5 golden replays) and a rules "golden"
fingerprint baseline.

```
dotnet run --project Tools/HeadlessTests/HotR.Tests -c Release
```

- Run it **before** your change (to confirm a green baseline) and **after**. Report both results.
- It must exit with code 0. A red harness means the task is not done.
- **Golden files** (`Tools/HeadlessTests/Golden/*.json`) may only be regenerated with `--update-golden`
  when the task prompt explicitly allows it. When you do, list every changed entry and explain why the
  change is intended.
- If `dotnet` is unavailable in your environment, say so explicitly in your report. Do not claim
  verification you did not run.
- Files that the harness cannot compile (MonoBehaviours) must be checked by careful reading: confirm
  every member you reference exists with the exact signature, and every `using` is present.

## 7. Determinism rules (gameplay)

`BoardModel` is deterministic: same level + seed + actions ⇒ same result. The golden replays depend on it.
- Do not change the order or number of `Rand()` calls on any code path the task does not target.
- Do not change iteration order (`OrderBy(...).ThenBy(...)`) of existing loops.
- Do not change `CampaignReplayRules.Fingerprint`.
- If a required change makes a golden replay fail, **stop and report**. Do not edit the fixture.

## 9. Working procedure

1. Read the task prompt, the referenced FINDINGS entries, and DECISIONS.
2. Locate code **by the quoted snippet**, not by line number (line numbers drift between tasks).
   If a snippet no longer matches, stop and report.
3. Make the smallest change that satisfies the acceptance criteria. Do not fix unrelated issues you
   notice; list them in your report instead.
4. Run the harness (§6). Re-read your full diff once, end to end.
5. Final report, in this order:
   - **Summary** (2–4 sentences).
   - **Files changed** with one line each.
   - **Acceptance criteria**: each criterion → PASS/FAIL with evidence (test name or reasoning).
   - **Harness output**: before/after pass counts, exit code.
   - **Not verified**: what needs Unity (copy the prompt's human checklist, adjusted to what you did).
   - **New strings** needing translation review (if any).
   - **Risks / follow-ups** you noticed but did not act on.
6. One task per branch (`codex/<task-number>-<short-name>`). Never mix tasks.
