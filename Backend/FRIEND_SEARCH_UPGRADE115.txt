# Friend-search schema 14 to 15: stopped owned staging upgrade

This upgrades an existing owned staging database from schema 14 to 15. It adds the ephemeral friend-search cursor table and indexes. It does not activate social features or contact a provider. New staging roots are initialized by the normal staging105 workflow; do not use this command on a new root.

1. Stop the supervised service and worker, and confirm the configured owned authority and its private descriptor. Preserve the original ownership marker, data directory, existing backups and all earlier upgrade receipts.
2. From the Backend directory, run `./.venv/Scripts/python.exe -B -m hotr_backend.staging_upgrade115 --manifest <private-descriptor-path> --name <fresh-backup-name>` (Linux: use the venv Python path). The name is at most 40 ASCII letters, digits, underscores or hyphens. Never put credentials in the command, logs or repository.
3. The command acquires both existing owned locks, verifies the owner and exact schema, seals an immutable schema-14 SQLite backup and an owner-bound receipt under the existing private backups directory, marks the upgrade pending, validates preserved rows, and commits only the additive schema change. It restores the existing Ready marker only after the completed receipt is durable. It does not replace the database.
4. If interrupted, keep the same data directory, ownership marker, backup, receipt and exact backup name; retry the exact same command. Do not delete pending markers or sidecars, adopt another database, or choose a fresh name for a pending operation. Pre-backup partial artifacts must be reviewed rather than deleted automatically. For an unfinished prior 112 upgrade, resume its exact original operation first; this command accepts only a Ready schema-14 authority or its own pending receipt.
5. Run the existing staging105 preflight and start workflow after successful upgrade, then create a new current-schema backup using staging_ops105. Preflight alone checks configuration and ownership; it does not certify that the service, gameplay worker or external provider has been exercised. Production deployment and live provider acceptance remain separate.

The upgrade is verified with disposable owned staging fixtures, including interrupted operations, lock contention, existing receipt replay and data preservation. It does not imply that any real environment has been migrated.
