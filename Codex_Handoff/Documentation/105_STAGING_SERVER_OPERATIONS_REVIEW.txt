105 - Owned staging server startup and recovery

REVIEWED_WITH_OPEN_ACCEPTANCE_GATES. The owner approved the next preparation
step while hosting/domain remained unconfigured. This checkpoint implements
and locally tests the Python staging startup and backup/recovery workflow.
It does not deploy a public service or change the installed Android app.

IMPLEMENTATION

A strict nine-field non-secret descriptor selects staging only, an owned HTTPS
origin, stable deployment/scope, private local data directory, loopback port and
optional VK/replay configuration. Unknown/duplicate fields, malformed types,
network/source-tree paths and invalid ownership are rejected. The checked-in
empty-origin example fails before initialization, database or service creation.

Initialization writes owned metadata, locks and disabled provider configuration,
not a database. Initialized permits exactly the first database creation. Ready
with a missing database and Initialized with an existing database/WAL/SHM are
blocked rather than silently resetting player state. RestorePending cannot
start. Stable ownership does not pin optional VK/replay/port settings, allowing
later approved configuration changes without replacing the database.

The launcher holds a lifetime OS runtime lock, a short control lock and an owned
127.0.0.1 socket before creating the database. It uses a controlled environment,
explicit managed/social services and unavailable commerce/ads/notifications,
then restores its caller environment on exit/failure. Worker pin checks do not
execute the worker or establish gameplay/provider acceptance. Each service run
gets a new owned rendezvous; old interrupted-run records remain history.

The ops wrapper delegates the existing SQLite backup/restore functions. Online
backup uses the control lock while serving retains its separate runtime lock.
Pending/Ready snapshot receipts bind origin/deployment/scope/root nonce to the
exact immutable backup bytes, size and current schema. Restore validates that
proof first, writes into a fresh owned RestorePending directory and marks it
Ready only after independent validation. It never overwrites the active database,
edits a descriptor, activates a replacement or discards failed/foreign artifacts.

App configuration export writes only the six public checkpoint104 fields to a
new external JSON file. Server paths, keys and optional provider settings never
enter that app payload. No active endpoint is committed or imported into Unity.

RETAINED FAILURES AND ENVIRONMENT GATE

Flow01 reached 50 checks and live backup but asserted listener closure before
Windows asynchronous Job termination completed. Its failure remains retained.
A separate CleanupRecheck01 confirmed both exact PIDs and the port absent, with
no follow-up kill. The corrected harness holds the already-owned server handle,
waits for its termination, then polls the known port. Flow02 is a fresh run.

The actual PowerShell -File probe was blocked by this PC's execution policy:
running scripts is disabled. Python was not reached, no data changed, and no
execution-policy override/bypass was applied. The PowerShell wrapper remains
blocked/unverified here. The existing Python CLI is the supported tested path;
the current guide documents it. Old guide/test/harness source snapshots and
their original evidence remain bound to their own epochs.
