## What remains unresolved

The browser page is a generic provider error with no HTTP status or reason code. A read-only Chrome DevTools tab listing confirmed that the **actual phone authorization request** uses client ID `54867814`, callback `https://api.novamind-it.ru/v1/identity/vk/callback`, response type `code`, and PKCE method `s256`. Only those public fields and query-key names were printed; `state`, challenge, code, and tokens were not logged. The query also has an empty `scope` and `prompt=login`. The owner reports that the VK Console application is active, is a Web app, and lists the exact callback. This is useful operator confirmation, though a Console screenshot/export or provider diagnostic has not been captured. The failure remains at VK's authorization page; the exact cause is not established.

With the owner's help, a read-only Chrome DevTools listener observed the visible VK error page while the owner tapped **Try again**. The page remained on VK's generic error; the listener saw `net::ERR_ABORTED` from the navigation but no HTTP 4xx/5xx response. Resource timing showed that the VK page loaded its own static assets and some VK telemetry calls, so this capture does not identify a blocked resource or a provider rejection code. The diagnostic printed only host/path, status, and error class—no full URLs, query values, cookies, credentials, or tokens. The phone was left in the owner's control.

The backend's token/user-info exchange puts its parameters in a form body. VK's [official Web SDK source](https://github.com/VKCOM/vkid-web-sdk/blob/master/src/auth/auth.ts) shows an authorization-code exchange with most context parameters in the query and the `code` in a form body. Both patterns might be accepted; the mocked backend tests cannot prove provider compatibility. This difference occurs **after** browser consent and therefore does not explain the current browser error. Recheck it with a real provider callback before enabling VK sign-in for release.

VK's [Web SDK URL builder](https://github.com/VKCOM/vkid-web-sdk/blob/master/src/utils/url/url.ts) uses the canonical `id.vk.ru` host and adds `v`, `sdk_type`, and `app_id`; the game's custom browser OAuth URL did not. The `.com` URL redirected to `.ru` on the phone; the backend token client deliberately refuses redirects, so both backend and Unity host handling were corrected together. A first manual diagnostic returned the same error, but its dummy `state` was too short to isolate the metadata question. A second browser-only diagnostic used a valid-length state, valid PKCE challenge, and the published Web SDK's authorization fields; the owner reported the same error in Chrome. This makes missing SDK metadata an unlikely sole cause. The diagnostic never completed sign-in and had no active game flow; no metadata was added to the live URL.

Source inspection found a separate UX issue: `ServerAccountService83.RefreshVkSignin` calls `OpenVkAuthorization` when the refreshed flow remains Pending. Thus the visible **Check VK status** action can reopen the browser rather than only report status. This was not re-exercised after cancellation in this phone run; a separate explicit browser-resume action should be designed before changing that behavior.

The provider-side diagnostic request is drafted at `Release/RuStore/VK_AUTH_PROVIDER_ESCALATION134.txt`. Before accepting VK sign-in, obtain a provider error code or configuration correction, install a client build that accepts `id.vk.ru`, then deploy the backend host change to staging. Deploying the backend change first would make the installed versionCode 130 reject its new authorization URL. Complete a real account consent and game return on the new signed Android build, then test new-player linking, existing-account selection, cancel, restart, and recovery. Do not share credentials or log OAuth codes or URLs. Keep the current guest progress intact until an explicit successful confirmation.
